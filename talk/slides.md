# AI 编程怎么真正跑起来

不是多开几个聊天窗口。
是 **人写规则，Agent 按规则干活。**

---

# 今天不讲这些

- 哪个模型最强
- Prompt 怎么写才「聪明」
- 替你生成一个完整产品

讲 **流程**：事情怎么进来、谁做、做到哪停、怎么复查。

---

# 聊天写代码，撑不久的三个原因

1. **上下文会漂** — 同一个 bug 换窗口，规则重讲一遍
2. **边界在人脑子里** — 「这个别自动关」只存在于某次对话
3. **做完没法关单** — 没有已处理 / 未处理，只会永远「请再验证」

---

# 四层，从人到系统

1. **对话** — 这一次，把一件事做完（PR / 评论 / 关掉）
2. **Skill** — 一种情况，一种做法
3. **Automation** — 规则仓库。改文件，行为跟着变
4. **产品也是 Agent** — 动作、MCP、eval，别人也能接进来

往下走一层，人就少说一遍。

---

# 第一层：一次对话只办一件事

同一条 PR、同一个 bug，留在同一个会话。
目标变了、Agent 漂了，就新开，第一条消息带锚点（PR 号 / 分支 / 约束）。

不要让一个窗口同时「改 CI、迁面板、讲跨平台」。

---

# 交给 Agent 的方式

把 **问题和成功标准** 交给它。

不要把「根因在第 N 行，改成 Y」写死。
猜的标成假设，允许它自己否定。

人只在不可逆的地方拍板：合并、对外口径、破坏性改动。

---

# 第二层：Skill

一个目录，一种情况。

```
---
name: inbox-triage
description: 新反馈还没分类时：先点名已处理 / 未处理，再打标。
---
# 步骤
1. …
```

**何时用、先看什么、自动做什么、何时停下来问人。**
写意图，不要写会死的工具参数。

---

# Skill 长什么样（真的）

| skill | 何时用 |
| --- | --- |
| issue-triage | 新 issue，或还没分拣 |
| need-more-info | 缺复现 / 版本 / 期望 |
| already-fixed | 当前代码已经没了 → 关单 |
| try-auto-fix | 带了 TryAutoFix，才允许开修 |
| dev-taste | 新功能一次补密度，别事后逐条调 |

来源：`qk-automation`。规则覆盖的直接做。

---

# 第三层：Automation = 规则仓库

Agent **先读规则，再读匹配的 skill，再动手。**

改 markdown，不用再跟 Agent 嗨。

最重要的一行：

```
mode: notify-only    # 只报，不动
mode: apply-skills   # 按表真正动手
```

监控可以一直跑。动手必须有开关。

---

# 动手之前先点名

**已处理 / 未处理。** 这是第一句话。

看时间线、关联 PR、维护者备注、当前主线。
不要只看用户正文。

已经没了 → 关 issue。不要用「请再验证」收尾。
还在 → 才分拣、摘要、或者修。

---

# 能自动 vs 必须停

**自动（不必问）**
- 能看清的 bug / 需求 / 问题 → 打标
- 缺信息 → 追问模板
- 已处理 → 关单
- 带 TryAutoFix 且改法局部 → 开修复

**必须停**
- 要不要做这个需求
- wontfix / 对外承诺版本号
- 改数据格式、密钥、花钱
- 只为这一个关键词打补丁

---

# 升级也要带球，不能把球踢回去

给负责人的三条：

1. 已经做了什么（先点名已处理还是未处理）
2. 建议怎么走（修 / 不修 / 等复现，三选一）
3. 反对时回哪一个词（「不修」「等下版」）

禁止只写：「先不改，等你定。」

---

# 第四层：产品自己也是 Agent

Quicker 已经能被外部 Agent 当工具用：

- `quicker_eval` — 跑 Host JS（不挂 chrome）
- `actions.search / export / validate / import`
- 写操作要开门；破坏性 API 即使开了门也拦

本机 loopback + Bearer。默认关。
测试可以在 Linux 上跑，不依赖 Windows 桌面。

---

# 现场演示 1：迷你 automation

打开本仓 `examples/mini-automation`。

一条假反馈走进去：

1. 先点名已处理还是未处理
2. 未处理 → `inbox-triage`
3. 缺版本 → `need-more-info`
4. 主线已经没了 → `already-done`，关单

规则在 `policies/decision-rules.md`。Skill 在 `skills/`。

# 现场演示 2：两个动作

**动作 A · 扔给分拣**
选中一段用户反馈 → 交给 Agent，按 inbox-triage 走。

**动作 B · 会前一页纸**
按 `examples/skills/meeting-brief` 生成一页可讲的会前简报。

人还是入口。Agent 是处理方式。动作是按钮。

# 真事一：审查机器人不是合并闸

自动审查会看旧文档，把合法字段打成错误。
也会抓到真的数据丢失。

所以：**瞥一眼，不当自动闸。**
合之前人看合同，不看语气。

---

# 真事二：损坏的信封不能当正文写盘

`write_file` 的 payload 以 `@@` 开头但头是坏的。
如果当「无头正文」写进去，目标文件就被覆盖。

做法：看起来像信封就 **拒绝**，清掉半成品正文。
能自动的那一层，也要 fail-closed。

---

# 真事三：Agent 能力要能在 Linux 测

核心契约（鉴权、eval、写门禁、导入导出）
如果只能在 Windows testhost 里跑，云端 Agent 就测不了。

把 live 装配和可测核心拆开。
`dotnet test` 在 Linux 过了，再合进主线。

---

# 人还要守的三道门

1. **合并** — Agent 可以开 PR，合是人的
2. **对外口径** — 不承诺版本号，不贴源码
3. **产品取舍** — 默认值、互斥匹配路、否过的方向，只升级

自动的越多，这三道越要硬。

---

# 带走

1. 一种情况，一个 Skill。写清何时停。
2. 规则放仓库。改文件，不要改聊天记录。
3. 先点名已处理 / 未处理。已经没了就关，不要请人再验证。

本仓可以当场翻：`examples/` 和 `talk/demo-script.md`。
